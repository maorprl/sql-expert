# Stage 1 learner route

The business request remains visible as context; it is not a learner step:

> The research team is reviewing media coverage and wants every article to include the source that published it.

This first JOIN encounter develops the ability to preserve one article per output row while adding its publishing source.

The route contains five top-level learner episodes. These episodes package the established reasoning sequence into a more continuous guided flow; they do not remove required reasoning moves or learner evidence.

1. **Identify relevant relations.** From the live schema, identify and add `news_article`, which contains the articles, and `news_source`, which contains publishing-source information, to the Working Schema. The task requires two relations; the Working Schema capacity of four is not a task target.

2. **Understand the relationship.** First identify `news_article.news_source_id` as the column that points from an article to its publishing source. Only after that reasoning, introduce Primary Key / Foreign Key and reveal that `news_article.news_source_id` (FK) references `news_source.news_source_id` (PK); the referenced source row contains `name`. Then answer the closed Cardinality question. Only after correct Cardinality reasoning, introduce Cardinality and annotate the same relationship as one news source to many news articles. PK/FK must not be exposed in the Working Schema before the connecting-key reasoning, and Cardinality must not be revealed before the Cardinality reasoning.

3. **Establish result grain, the baseline, and predict behavior.** Once the relationship and cardinality are established, identify what one requested result row represents: one news article. Only then introduce **NEW CONCEPT: GRAIN**: the grain of the requested result is what one requested result row represents. Grain is not a property of `news_article`, and it is not another name for a table. The business request already orients the output around articles; making the row meaning explicit here prepares the learner to reason about preserving it. Use a dedicated compact Baseline SQL editor, prefilled with `SELECT COUNT(*) FROM news_article`, to run and interpret the baseline measurement. It reports **Baseline result: 18 rows**, and the learner identifies 18 as 18 starting news-article rows. The Baseline editor is a local measurement tool and does not persist into JOIN implementation. Without resetting the reasoning journey into a disconnected task, predict before JOIN vocabulary is introduced that adding the publishing-source name preserves 18 rows with the same result grain. The explanation connects the result grain, baseline, and one-source PK/FK match: **one article per result row → 18 starting article rows → one matching source per article → 18 result rows with the same grain**.

4. **Choose the semantic relational action.** Choose to combine each news article with its related news source, then introduce **NEW CONCEPT: JOIN**. JOIN terminology does not appear before this semantic choice.

5. **Learn JOIN, implement SQL, and verify.** Treat the JOIN introduction as the instructional climax of Stage 1. Before learner-authored SQL, explicitly connect the reasoning already established to the relational operation and its SQL expression. Keep the Working Schema as the schema-level anchor, and use a separate local row-level example to show one article row matching one source row through the established `news_source_id` relationship and contributing `title` + source-name information to one result row. Then show that the already-established relationship becomes the `ON news_article.news_source_id = news_source.news_source_id` condition, and reconnect the business request to the full query structure: requested attributes → `SELECT`, starting article rows → `FROM news_article`, adding related source information → `JOIN news_source`, established relationship → `ON`. Previously established Grain, PK/FK, Cardinality, and the 18-row baseline are reused rather than re-taught. Only after this explanation does a separate clean SQL implementation editor become the primary action surface. The learner writes a result-checked query returning each article's `title` with its publishing source under the output name `source_name`. The exact desired output contract is available on demand as optional scaffolding — `title | source_name` — rather than being permanently exposed as part of the primary task prompt, and revealing it is not counted as Hint 1 / Hint 2. After successful execution, the learner inspects the actual result and verifies it against the earlier prediction while that result evidence remains visibly associated with the verification task: 18 rows, correct article/source association, and one news article per row. The learner still explicitly answers the final-grain verification question.

Stage completion is a state, not a numbered episode. Completed work remains compact, quiet, and reviewable. Required reasoning evidence must remain inspectable even when multiple reasoning moves occur inside one top-level episode; review retains the original question or task, learner answer or selection, completion state, relevant feedback or concept consequence, and any opened hints.
