# Lesson 1 learner route

The repository path retains the historical/internal `stage-1` name. The learner-facing product label is **Lesson 1**.

The business request remains visible as context; it is not a learner step:

> The research team is reviewing media coverage and wants every article to include the source that published it.

This first JOIN encounter develops the ability to predict the row effect of the current JOIN from a chosen baseline by reasoning about how many matching rows each baseline row contributes. In this case, the learner predicts that adding publishing-source information preserves one article per output row.

## Lesson gist — Matching

Lesson 1's conceptual identity is **Matching**: one article row matches its related source row through the established relationship. The organizing causal argument is that result rows for this INNER JOIN step correspond to matching row pairs, so the learner can predict the row-count effect relative to the chosen article baseline by determining how many matches each article row contributes. JOIN expresses that match and adds publishing-source context while the requested result remains one article per row. This model is scoped to the current JOIN step before unrelated row-changing operations; it is not a universal final-row-count formula for arbitrary SQL.

PK/FK, Cardinality, Grain, baseline, prediction, JOIN, ON, SELECT, and verification support that single causal argument rather than functioning as parallel lesson topics. This gist organizes the teaching and completion of the Lesson; it does not replace or remove any required reasoning move below.

The route contains five top-level learner episodes. These episodes package the established reasoning sequence into a more continuous guided flow; they do not remove required reasoning moves or learner evidence.

1. **Identify relevant relations.** From the live schema, identify and add `news_article`, which contains the articles, and `news_source`, which contains publishing-source information, to the Working Schema. The selected-state wording is `Added`. The task requires two relations; the Working Schema capacity of four is not a task target.

2. **Understand the relationship.** First identify `news_article.news_source_id` as the column used to locate related publishing-source information. Only after that reasoning, introduce Primary Key / Foreign Key and reveal that `news_article.news_source_id` (FK) references `news_source.news_source_id` (PK); the referenced relation contains the needed `name`. Do not translate those facts into the first-direction answer. The learner reasons that PK uniqueness permits at most one matching source row and that the non-null, satisfied FK requires at least one matching source row, then combines those premises to establish exactly one matching source row for an article. This is a supported first-exposure relational deduction, not evidence of independent Cardinality mastery. The learner then reasons in the reverse direction that one source can be related to potentially many articles. `Venture Daily → 6 articles` may illustrate that already-reasoned reverse direction, but the complete four-source/18-match comparison must remain hidden before the protected article-baseline prediction. Only after both directional meanings are established, introduce Cardinality and annotate the same relationship as one news source to many news articles. PK/FK must not be exposed in the Working Schema before connecting-key reasoning, and Cardinality must not be revealed before the Cardinality reasoning.

3. **Establish result grain, the baseline, and predict behavior.** Once the relationship and Cardinality are established, identify what one requested result row represents: one news article. Only then introduce **NEW CONCEPT: GRAIN**: the Grain of the requested result is what one requested result row represents. Grain is not a property of `news_article`, another name for a table, the baseline, or the SQL `FROM` relation. The business request informs the requested row meaning; it is not equivalent to Grain. The business request already orients the output around articles; making the row meaning explicit here prepares the learner to reason about preserving it. Use a dedicated compact Baseline SQL editor, prefilled with `SELECT COUNT(*) FROM news_article`, to run and interpret the baseline measurement. It reports **Baseline result: 18 rows**, explicitly interpreted as 18 starting article rows. The Baseline editor is a local measurement tool and does not persist into JOIN implementation. Without resetting the reasoning journey into a disconnected task, predict before JOIN vocabulary is introduced that adding the publishing-source name preserves 18 rows with the same result Grain. The learner's reasoning is: for this INNER JOIN step, result rows are matching article/source pairs; each baseline article contributes one such pair; therefore 18 baseline articles predict 18 result rows. After the learner commits to that prediction, a compact explanatory visual shows `1 article row → 1 matching source row → 1 result row`, then scales that reasoning to the 18-row case. The explanation connects the result Grain, baseline, and one-source match: **one article per result row → 18 starting article rows → one matching source per article → 18 result rows with the same Grain**. Only after this commitment may an aggregate `4 source rows → 18 matching pairs/result rows` contrast appear; if learner-facing at all, it should preferably be optional or later enrichment and must not compete with the article-baseline argument.

4. **Choose the semantic relational action.** Choose to combine each news article with its related news source, then introduce **NEW CONCEPT: JOIN**. JOIN terminology does not appear before this semantic choice.

5. **Learn JOIN, implement SQL, and verify.** Treat the JOIN introduction as the instructional climax of Lesson 1. Before learner-authored SQL, explicitly connect the reasoning already established to the relational operation and its SQL expression. Keep the Working Schema as the schema-level anchor, and use a separate local row-level example to show one article row matching one source row through the established `news_source_id` relationship and contributing title and source-name information to one result row. Then show that `ON news_article.news_source_id = news_source.news_source_id` expresses how rows match using the already-established relationship, and reconnect the business request to the full query structure: `FROM` starts the article rows; `JOIN` brings the matching source row; `ON` defines how rows match; and `SELECT` chooses the article and source fields in each result row. Because each article contributes one matching pair, the result remains one article per row. Earlier explanations remain available and reviewable as this teaching sequence progresses, while the active explanation receives stronger focus. Previously established Grain, PK/FK, Cardinality, and the 18-row baseline are reused as supporting parts of the same match-contribution argument rather than re-taught as separate topics. Only after this explanation does a separate clean SQL workspace become the primary action surface. The learner writes a result-checked query returning each article's `title` with its publishing source under the output name `source_name`. The exact desired output contract is available on demand as optional scaffolding — `title | source_name` — rather than being permanently exposed as part of the primary task prompt, and revealing it is not counted as Hint 1 / Hint 2. The semantic validator may report that the executed result satisfies this task contract. The learner still inspects the actual result and explicitly answers the final interpretive verification question, connecting the evidence to the earlier baseline-relative 18-row prediction and one-article-per-row Grain.

Lesson completion is a state, not a numbered episode. Completed work remains compact, quiet, and reviewable. Required reasoning evidence must remain inspectable even when multiple reasoning moves occur inside one top-level episode; review retains the original question or task, learner answer or selection, completion state, relevant feedback or concept consequence, and any opened hints.
